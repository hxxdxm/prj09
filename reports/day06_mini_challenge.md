# Day 06 Mini Challenge

## 검사 대상
Ch.-B. 제품 코드

## 사용한 데이터
새로운 제품 이미지 4장

## 바꾼 OCR 설정
SN 검사: 숫자만 (Whitelist 0~9, Regex ^[0-9]{13}$)
Mini Challenge: 영문 대문자 + 숫자 + - (Regex ^[A-Z0-9-]+$)
추가 검사: ^[A-Z]{2}[0-9]{6}-[0-9][A-Z]$ (실제 Ch.-B. 모양)

## 실패한 이미지
파일: 0386316000696_side.png
OCR 결과: TI776224-20
실제 값: TI776224-2D
다시 사용해 본 전처리: gray → TI776224-20, clahe → T1776224-20
결과가 좋아졌는가?: 아니요. clahe는 I를 1로 잘못 읽어 오히려 나빠졌다.

원인: 4장 중 가장 흐린 사진이라 마지막 글자 D와 숫자 0의 모양이 비슷해졌다.
전처리로는 사라진 글자 모양을 되살릴 수 없었다. (본 실습 Blur 실패와 같은 원인)

## 발견한 문제
처음 실행할 때 Ch.-B. 바로 위의 SN 줄을 ROI로 잘못 선택했다.
OCR은 SN 13자리를 정확히 읽었고 교재 Regex도 4장 모두 통과했지만,
엄격한 Regex는 4장 모두 False로 나와 "검사 대상이 아닌 영역을 읽었다"는 것을 알려 주었다.
저장된 ROI 파일을 지우고 Ch.-B. 줄을 다시 선택해 해결했다.

## 확인한 점
SN에서 사용했던 ROI → OCR → 문자열 정리 → 형식 검사 → 실제 값 비교 과정을
다른 문자 코드에도 Whitelist와 Regex만 바꿔 다시 적용할 수 있었다.

교재 Regex(^[A-Z0-9-]+$)는 틀린 값 TI776224-20과 잘못 선택한 SN도 통과시켰지만,
실제 코드 모양에 맞춘 엄격한 Regex는 둘 다 잡아냈다.
정답을 모르는 실제 검사에서는 형식 검사를 구체적으로 만들수록 OCR 오류와 ROI 실수를 더 많이 걸러낼 수 있다.
